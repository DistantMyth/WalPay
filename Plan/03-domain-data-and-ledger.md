# Domain model, database constraints and financial observations

Proposed canonical data model. PostgreSQL is the durable authority for WalPay records. A journal records observed external money movement and business obligations; it does not make a user balance available to spend. Never name an aggregate `wallet_balance` or let a journal credit authorize a new payment.

## Shared types

IDs: UUIDv7 generated by an audited library; they are identifiers, never authorization secrets. Store provider IDs separately as text. UTC timestamps use `timestamptz`; preserve the user's IANA timezone for calendar budgets. Amounts are integer minor units in JSON strings and database `numeric(30,0)` with a strict application/provider upper bound. Currency exponent metadata is versioned and product-specific availability is separate. All `Money` values are unsigned; debit/credit or adjustment direction is a separate field.

```ts
type Money = { currency: string; amount_minor: string };
type RuntimeMode = 'simulation' | 'sandbox' | 'live';
type Principal =
  | { kind: 'user'; userId: string; tenantId: string; sessionId: string }
  | { kind: 'partner'; partnerId: string; tenantId: string; scopes: string[] }
  | { kind: 'service'; serviceId: string; scopes: string[] };
```

Never parse amount through `Number`. The database decimal string driver mapping is mandatory. Overflow is checked before BigInt multiplication/serialization at provider boundaries. USD is primary reporting currency; conversions are separate attributed valuation records, as specified in 15.

## Representative SQL

SQL sketches require migrations and tests; foreign-key targets are abbreviated. Enforce the same numeric grammar in the application before insertion because SQL numeric casts can round fractional input.

```sql
CREATE TABLE payment_intents (
  id uuid PRIMARY KEY,
  tenant_id uuid NOT NULL,
  owner_user_id uuid NOT NULL,
  mode text NOT NULL CHECK (mode IN ('simulation','sandbox','live')),
  purpose text NOT NULL,
  payee_binding_id uuid NOT NULL,
  currency char(3) NOT NULL,
  amount_minor numeric(30,0) NOT NULL CHECK (amount_minor > 0),
  quote_id uuid NOT NULL,
  financial_digest text NOT NULL,
  status text NOT NULL,
  version integer NOT NULL DEFAULT 1 CHECK (version > 0),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, id)
);

CREATE TABLE provider_operations (
  id uuid PRIMARY KEY,
  tenant_id uuid NOT NULL,
  intent_id uuid,
  binding_id uuid NOT NULL,
  kind text NOT NULL,
  business_key text NOT NULL,
  provider_request_id text NOT NULL,
  request_digest text NOT NULL,
  status text NOT NULL,
  attempt_count integer NOT NULL DEFAULT 0,
  lease_owner text,
  lease_until timestamptz,
  submitted_at timestamptz,
  next_reconcile_at timestamptz,
  UNIQUE (binding_id, kind, business_key),
  UNIQUE (binding_id, provider_request_id),
  FOREIGN KEY (tenant_id, intent_id)
    REFERENCES payment_intents (tenant_id, id)
);

CREATE INDEX operations_recovery
ON provider_operations(next_reconcile_at)
WHERE status IN ('submitted','outcome_unknown');
```

Use composite tenant-aware FKs on all tenant-scoped relations. A globally valid object ID must not let one tenant reference another tenant's quote. Add explicit status enums/checks in actual migrations from the canonical register. Avoid live provider response JSON as the only source for searchable critical fields.

## Atomic budget reservation

Design a bucket per principal + policy + currency + UTC window derived from the configured calendar timezone. A mission can also have a per-intent cap. If several buckets apply (mission/day/month), lock them all in ascending bucket ID order and update in one transaction. Do not hold database locks during LLM/provider network calls.

```sql
UPDATE budget_buckets
SET reserved_minor = reserved_minor + :amount,
    version = version + 1
WHERE id = :bucket_id AND currency = :currency
  AND spent_minor + reserved_minor + :amount <= cap_minor
RETURNING id;
```

Insert the uniquely keyed reservation in the same transaction; a duplicate rolls the transaction back and returns the existing reservation. Missing returned row means budget denied. Capturing success moves reserved to spent in the same accounting transaction exactly once. Definitive failure releases it. An expired quote releases only if no provider operation is outstanding; `outcome_unknown` remains reserved even if the original TTL has passed. Refund treatment is explicit: default gross spending policy does not replenish daily budget automatically; a user-visible net policy can be added as a distinct version.

## Observational journal

Use an append-only balanced journal to prevent inconsistent earnings/reporting projections. Each account is scoped to a legal entity and currency, and is typed as observed provider clearing, observed gross revenue, provider fees, refunds or payout settlement. Personal expense records use their own reporting entity; do not mix a merchant's books with a shopper's observations.

Example for a merchant capture USD 10.00 with verified provider fee USD 0.59: debit `observed_provider_clearing` 941; debit `observed_provider_fee_expense` 59; credit `observed_sales_gross` 1000. This is a reporting model, not accounting/legal advice or proof of withdrawable funds. If fee is not yet known, record gross payment observation and a suspense projection; do not manufacture net or fee. Post the complete journal once verified facts are available or use an explicitly reversible accrual rule.

Each transaction's debits equal credits within one currency and entity. Use a deferred constraint trigger or a posting function that forbids writes outside the posting service; test incomplete transactions cannot commit. Journal lines cannot be updated/deleted by application role. Corrections reference the original transaction and add a full or partial reversal with reason and source observation. Deduplicate economic postings by canonical `(provider_binding_id, resource_type, provider_resource_id, fact_kind, financial_revision, entity_id, accounting_rule)`, not observation ID: API responses and several webhooks may observe the same capture. Each observation links to one canonical financial fact. Accounting rule/version changes cannot authorize another economic posting; use a reviewed reversal/repost migration. Separately typed task-approval accruals use a unique obligation key, remain distinguishable from provider settlement, and never create spendable funds.

FX uses separate balanced legs per currency with an attributed conversion observation; it never sums USD and EUR in one balancing equation. Estimated USD valuations are outside settled journal facts. The earnings view presents gross, known fees, refunds, pending and settled, with `coverage` describing which provider/partner records WalPay actually sees.

## Inbox, ordering and replay

Persist raw webhook body securely with a content hash and configured binding. Initial PayPal ingress performs synchronous official signature postback verification before success acknowledgement, then commits verified inbox persistence before ACK. A verification dependency outage returns a retryable transport failure and never applies financial effects. A later alternative can durably accept an explicitly untrusted inbox item and verify asynchronously with monitoring, but must be designed/deployed as a separate acknowledged policy; no financial effects occur before verification. Duplicate same ID/same body is a no-op. Same ID/different body is quarantined and alerts. Different event IDs can describe the same capture; canonical financial fact/resource uniqueness still deduplicates.

Event order is not guaranteed. Transition using current provider resource facts, not arrival order. A capture completion arriving before local order-created processing can create a pending link and schedule fetch, but cannot invent owner/payee. An old pending event never downgrades confirmed completion. Reversal/refund/dispute facts are separate lifecycle records, not a downgrade to `failed`.

Projection consumers record processed event ID and projection version in one transaction. Rebuild starts from a checkpoint and immutable records. Rebuild into new tables then compare and switch; do not truncate live reporting during a demo.

## Tenant isolation, retention and schema evolution

Use application-scoped queries plus PostgreSQL row-level security as defense in depth. A non-owner API role gets tenant context through `SET LOCAL` inside every transaction, never a session setting that leaks through a connection pool. Background/admin roles have narrow audited privileges. RLS owners and bypass roles need separate treatment. [PostgreSQL row security](https://www.postgresql.org/docs/18/ddl-rowsecurity.html).

Migration pattern: expand nullable/new columns -> compatible code -> bounded backfill -> validation -> switch reads -> contract in later release. Use `lock_timeout` and statement timeouts. Separate app and migration roles; app cannot alter schema. Seed scripts are idempotent and refuse live mode by default. Receipt/contact deletion follows consent/retention rules; financial/audit records with a legitimate retention requirement use pseudonymization and documented access, not unbounded retention by convenience.
